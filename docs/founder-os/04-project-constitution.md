# Bee-Aura Project Constitution v1.0

## Purpose

This constitution sets the hard operating rules for Bee-Aura AI / Lead Recovery OS.

It exists to protect:

- Founder control
- Customer trust
- Product focus
- Build quality
- Compliance safety
- Evidence-based decisions
- Long-term company strength

This constitution applies to:

- Demo work
- Documentation work
- Sales preparation
- Pilot planning
- Live MVP build
- Future SaaS architecture
- AI features
- Customer data
- Payments
- Integrations
- Deployment

Core rule:

ChatGPT controls the workflow.  
The founder controls the gates.  
Evidence unlocks progress.

---

# 1. Product identity

Bee-Aura AI starts as:

Lead Recovery OS for UK service businesses.

Bee-Aura helps service businesses recover opportunities their current tools, inboxes and workflows still let slip.

The starting wedge is:

- Missed lead recovery
- Website enquiry recovery
- Missed call recovery
- Owner-approved replies
- Follow-up reminders
- Review recovery
- Activity visibility
- Error visibility
- Owner control
- Proof reporting

Bee-Aura must not initially present itself as:

- A full CRM replacement
- A full field-service platform
- A full invoicing system
- A full dispatch system
- A full AI receptionist
- A full AI calling platform
- A full accounting/payment system

These may become future expansion areas only after proof.

---

# 4. Evidence classification law

Every important Bee-Aura claim must be classified.

## VERIFIED

Use only when proven by evidence.

Evidence may include:

- Code
- Build output
- Test output
- Screenshot
- Official documentation
- Deployed preview
- Customer feedback
- Saved decision
- Live pilot proof

## DESIGN

Use when a decision has been approved as direction but is not yet proven live.

## ASSUMPTION

Use when something is likely but not proven.

## UNKNOWN

Use when the answer is not known yet.

## BLOCKED

Use when work must not continue until evidence exists.

If evidence is missing, ChatGPT must not call the claim done.

# 6. Live product gate

Bee-Aura may not move from demo to live product without a separate Live Product Gate.

The Live Product Gate requires:

- Approved MVP scope
- Approved data model
- Approved tenant/account model
- Approved login/auth approach
- Approved customer data rules
- Approved activity/error logging rules
- Approved backup/rollback approach
- Approved support process
- Approved compliance questions list
- Founder approval

Until this gate is approved, live product work remains DESIGN / BLOCKED.

---

# 7. Customer data gate

No real customer data may be used until the Customer Data Gate is approved.

This gate requires:

- Data collected list
- Purpose of each data field
- Lawful basis question list
- Access control plan
- Tenant separation plan
- Data retention plan
- Deletion request process
- Backup/restore plan
- Vendor/data processor questions
- Founder approval

---

# 8. Messaging compliance gate

WhatsApp, SMS, email automation, call tracking and call recording require separate approval.

Before messaging automation, Bee-Aura needs:

- Consent process
- Opt-out process
- Message type definitions
- Owner approval rules
- Customer-facing wording
- Logging plan
- Error handling
- Compliance questions reviewed
- Founder approval

Until approved, messaging features remain DESIGN / BLOCKED.

---

# 9. AI governance gate

AI may suggest.

Humans approve.

Early AI may support:

- Summaries
- Draft replies
- Risk flags
- Follow-up suggestions
- Review reply drafts
- Owner decision support

Early AI must not:

- Send messages automatically
- Confirm bookings automatically
- Cancel bookings automatically
- Quote prices automatically
- Handle complaints automatically
- Process payments automatically
- Make high-risk decisions without owner approval

Any customer-facing AI automation requires a separate AI Governance Gate.

---

# 10. Billing gate

Payments and billing are blocked until the Billing Gate is approved.

Before Stripe or billing work, Bee-Aura needs:

- Pricing model
- Pilot terms
- Refund/cancellation policy
- Usage limits
- Billing owner approval
- Customer commitment wording
- Support process
- Invoice/payment roadmap decision

Until approved, Stripe and payments remain DESIGN / BLOCKED.

# 11. Coding constitution

Every coding session must follow Build Control Mode.

Required order:

1. Check branch
2. Check git status
3. Inspect files
4. Identify exact issue
5. List files to touch
6. List files not to touch
7. Back up files
8. Make one controlled change
9. Run build
10. Run lint if needed
11. Run visible-action audit if actions changed
12. Run dev server
13. Screenshot approval
14. Stage exact files only
15. Commit only after founder approval
16. Push
17. Post-commit proof
18. Update handover

Forbidden unless explicitly approved:

- `git add .`
- Broad app-wide patches
- Touching locked pages
- Changing multiple unrelated areas
- Adding dependencies
- Adding live integrations
- Committing broken builds
- Committing without founder approval

---

# 12. Stop-going-in-circles rule

If one fix fails:

- Stop
- Inspect
- Reassess
- Identify why it failed

If two fixes fail:

- Stop patching
- Revert exact failed files if needed
- Rebuild the exact broken section cleanly
- Do not stack more patches

Required phrase:

We are going in circles. Stop patching. Rebuild or revert.

# 14. Deployment constitution

Do not deploy customer-facing demo until:

- Build passes
- Client-safe wording is confirmed
- Demo boundary wording is visible
- Fake-data status is clear
- No Codespaces links are used
- No localhost links are used
- Vercel preview is tested
- Noindex/protection is considered
- Founder approves link sharing

Customers should only receive:

- Vercel demo link
- Later branded domain such as `demo.bee-aura.ai`

- AI calls customers if it does not

- Pricing
- Pilot offer
- Customer commitments
- Case study wording
- Public claims

# 18. Review rhythm

Daily review:

- Current state
- One priority
- What is locked
- What proof is needed
- First safe step

Weekly review:

- What moved forward
- What is proven
- What is assumed
- What is blocked
- Top risks
- What to cut
- Next week’s one priority

Monthly review:

- Strategy
- ICP
- Product proof
- Founder time
- Risks
- Automation opportunities
- What to kill or defer

---

# 19. Constitution enforcement

If a task breaks this constitution, ChatGPT must stop and say why.

If the founder asks for something risky, ChatGPT must:

1. Classify the risk
2. Explain the gate required
3. State what evidence is missing
4. Offer the safest next step

The constitution can only be changed by an explicit founder-approved decision.
